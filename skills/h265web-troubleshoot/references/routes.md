# 协议、音频、时间线与VR专项

### 8.4 直播、WebRTC、音频与VR专项

- HLS：先查master实际选择的variant，再查media playlist首片及持续刷新；分片地址基于最终playlist URL解析；不通过删EXT-X-KEY、改ENDLIST或改标签冒充支持。当前source-session选variant的逻辑也不等于自动自适应码率功能。
- H.264 HLS冻帧：先区分CORS/COEP加载阻断、直播清单尚未积累足够分片与实际解码/呈现冻结，核对实际核心（`mse_hls`不等于native）。重复SPS/PPS后面的P帧曾被上游误标关键帧/TS随机访问指示（RAI）；对照NAL、slice类型、真实IDR及封装标记，参数集或RAI本身不证明IDR，非IDR的I片也不能混同IDR。修复源码后还需确认运行二进制的构建/部署身份；不能用换核或播放器PTS偏移代替判因。
- HTTP/WS-FLV/TS：确认服务器注册真实流，再检查首个header/关键帧；代理buffering、断开、GOP等待、时间戳不连续分开定位。推流示例只针对测试流，并说明Ctrl+C停止；诊断不能默默改用户直播源。
- ZLM：文档中的`modify_stamp=1`/`paced_sender_ms=0`来源于特定RTMP→RTC验证，不是所有HLS/所有服务器的万能修复；先确认版本、路线、输入时间线和受影响范围。用户服务器配置改动另按其任务授权执行。
- WebRTC：WHEP信令HTTP成功后检查连接/协商与真实接收帧；ICE不可达时检查部署方提供的候选与TURN，不给伪造公网TURN。接收播放和WHIP推流的权限、媒体流所有权分开。
- A/V：区分初始起播与长播漂移，录制/采集音频实际输出时钟和视频实际呈现；毫秒与秒注明。`on_play_time`本身不是两条实际输出时钟的差值，原生统一时钟也不证明实测零漂移。HTTP-FLV输出限速诊断要核对AudioContext是否running；suspended时冻结的输出时间不能当作活时钟。当前首帧/AAC对齐修复不外推到所有协议。
- 性能：对照相同源/设备/核心/并发，检查网络、CPU、解码帧、GPU/context和释放；缩小canvas不降低源解码成本。降低源分辨率/帧率/GOP等应作为明确的源端试验，不冒称SDK优化。
- VR：真实单目ERP、有效投影、已启用鼠标/触摸；开VR前CORS资源准备和运行中跨域video切换限制分别处理。`get_vr_view()`返回请求状态，渲染降级看错误；非致命VR不触发选核/重载。
- 鉴权：一次性token重试要重新拿，不能把401变成循环retry；录像302后还要验证最终下载地址权限和Range。诊断素材优先自生成或可公开小样本。


适用路线/条件状态见[能力矩阵](capability-matrix.json)。当前稳定音量与实验性SR见[增强合同](enhancements.md)。音量均衡先检查实际 enum、config、`set_audio_leveling`/`get_audio_leveling_state`；策略已请求≠音频路径已生效。冻结732e173无此API，不能让用户套用新API到旧CDN。

排查失声或测量稳定音量时，进程静音不等于没有音频；结合真实输出波形/时钟判断，`captureStream()`也不证明最终设备输出。输入RMS过低表示增益测量缺少有效信号，不能直接判SDK失声或宣称增益通过。保持原测量阈值和输出比率要求；信号不足时可继续同档连续取样并保留全部样本，不能重采样丢弃错误输出。整源静音结论需完整独立解码；长源片段抽样只证明抽样范围静音，零输出不能证明有声时的增益正确。没有物理试听就保留此证据边界。

帧数持续增长但媒体时间几乎不动时，先按[上游时间线压缩排查](upstream-timestamps.md)比较源FLV、配置tag与服务端TS的DTS，再核对实际运行构建。重复AVC配置丢失时戳的一类RTMP→TS模式2问题已有源码修复及隔离验证；原失败仍保留，未部署服务不能算已修复。不要以切mode1、修改播放器时钟或重启用户服务代替诊断；原WebRTC场景建议不被此结论替换。
